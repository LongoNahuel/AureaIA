## 2) F1 — Estabilidad core (`ad1b0b1`, `31532a5`, `04dbe1d`)

- **RLock en StreamManager**: `acquire/release` corren concurrentes desde UI y analíticas;
  sin lock se duplicaban workers (hay test de regresión con 8 hilos). Nuevo `stop_device()`.
  `stop_all()` con join (logout→login acumulaba sockets zombies).
- **Timeouts RTSP** (`OPEN/READ_TIMEOUT_MSEC=10s`) + `rtsp_transport;tcp` global: un
  `cap.read()` contra una cámara caída "sucio" colgaba el hilo para siempre.
- **Cascadas FK + `PRAGMA foreign_keys=ON`** (listener solo-sqlite, portabilidad):
  borrar cámara limpia configs/reglas/eventos/media y apaga sus workers ANTES del delete.
  `alarm_events.rule_id` → SET NULL (borrar una regla no borra historial; la severidad ya se
  copia al evento). Índice `(device_id, timestamp)`. **La DB dev se recrea** (borrar
  `data/aurea_vms.sqlite3`).
- `_record_clip` tenía `try/finally` SIN except: fallas de escritura morían en silencio.
  `os.startfile` → `QDesktopServices` (permite probar clips en Linux).

## 3) F2 — Storage indexado + retención (`7dc39f6`, `b7e25a4`)

El requerimiento textual de Dani. Nueva tabla **`media_assets`** (única fuente de verdad de
clips/capturas/futura grabación continua): tipo, cámara, evento, `created_by` (usuario;
NULL=sistema), timestamp, **ruta relativa** con `/` (el data-dir puede moverse), tamaño,
duración, dimensiones. Índices `(kind,timestamp)` y `(device_id,timestamp)`. Layout físico
`data/media/<tipo>/<AAAA>/<MM>/<DD>/<cámara>/<HHMMSS>_<evento>.<ext>` — navegable a mano
pero **el código jamás lo escanea**. `alarm_events` perdió `snapshot_path/clip_path`; el feed
resuelve la media de 200 filas en UNA query (`list_media_for_events`).
**RetentionWorker**: purga por edad (7d) y tope (5GB) decidiendo contra la DB, margen de 120s
para no tocar clips en curso, knobs en Sistema → Grabando. Antes el disco crecía sin límite.
